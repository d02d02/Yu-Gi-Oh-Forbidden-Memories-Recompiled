# Anime Style mod — plan and map of what is needed (branch `adhoc-anime-art-mod`, from the v0.3.0 tag)

A standalone mod (`mods/anime-art/`, id `anime-art`) that gives every card an anime-style full-bleed frame, independent of
Forbidden Memories HD. Base: the upstream **v0.3.0 tag** (`663626b1d`), not master. Started 2026-10-12.

## Verdict in one paragraph
v0.3.0's engine already has everything the frame needs (`card_layout`: frame styles, rules, positions, digits). So the mod is
**data only**: a `mod.json` plus power-of-two PNGs. **No engine change and no code mod are needed for the frames.** The open
work is (1) deciding which retail cards get the purple/ritual-monster/god frames and tagging them, (2) looking at it in game.

## Not needed (and why)
- **Engine/C changes** — `card_layout` ships in v0.3.0 (`feat/anime-frame-standalone` is an ancestor of the tag).
- **The HD pack, or its `textures` key** — `textures` is a texture-pack replacement of game graphics; frame images are read by path
  relative to the mod directory. This mod declares no `textures`, `assets`, `library`.
- **A code mod (`library`)** — the host API has no call to choose a frame, set a card's tags or colour, or touch layout at run time
  (`card_tag` only *reads*; `hook` hooks guest game functions; `overlay` draws over the finished picture). Frames are decided by
  `frame_for` from data. A code mod could not fix the mip bug either (it is a static host function in `texture_pack.c`).
  A code mod would only make sense for something new (e.g. extra overlay drawing); none is planned.
- **Per-mod settings code** — declarative `settings` in `mod.json` are enough (the Mods window draws them).

## Traps
1. **One `card_layout` wins** (the last applied mod that declares one; not merged). `after: ["forbidden-memories-hd"]` makes this mod
   apply later, so it wins when both are installed; with HD alone this mod is simply absent.
2. **Power-of-two images** until the engine fix upstream: v0.3.0 `bank_halve` builds an incomplete OpenGL mip chain for other sizes ->
   frame invisible at Internal 2x/4x (fine at 1x). The fix is branch `debug/v0.3.0-frame` commit `490bb49ef`; see the shared notes
   `anime-frame-4x-bug.md`. Every size here must keep halving to 1 without an odd step (1024 and 2048 do; 600, 861, 919, 1319 do not).
3. Frame art must stay the **light originals** (no contrast boost: that was made for the old single 177x254 texture, obsolete since the
   3x3 tile grid in `card_layout_art.c`).

## Decisions (user, 2026-10-12)
1. **Fusion (and any per-card frame) is chosen by the mod user**, not by us: a list "card -> frame style", with examples in the README.
   Syntax: card id, or a card name, to a style name (`fusion`, `ritual_monster`, `obelisk`, ...). **A card we do not name is left exactly as
   it is: we never write a name, description, art, password or stats.**
2. **Ritual monsters**: the results of the game's ritual table get the `ritual_monster` frame (the user can still override per card).
3. God frames stay, for card mods and for the per-card list.
4. The mod ships as **one zip** with the images inside; the repo folder `mods/anime-art/` is the mod (PNGs committed there).
5. **On by default** (`enabled`, `full_bleed`). More options below.

## How the per-card choice works (checked on v0.3.0; **no code mod is possible**, and none is needed)
- The frame rules in `mod.json` pick a style by `class`, `tag` or `setting`. A card's tags come from a `cards` entry
  (`{"replace": <id or name>, "tags": [...]}`), so **choosing a frame = tagging the card**. The user writes that in a small mod of
  their own (README + `examples/my-anime-frames`), by card name or id: this is the syntax asked for.
- **A code mod cannot do it on the stock v0.3.0 engine.** The idea was to hook `Cards_HasTag` and answer from a list, but only the
  game units are built with `-fpatchable-function-entry`; `src/pc/cards/cards.c` (the port) starts at `push ebp` with no hook room
  (llvm-objdump of `cards.c.o`), and `host->hook` is documented for `src/game` functions. The frame choice itself (`resolve_style`)
  is port code too. A code mod could not fix the mip-chain bug either (static host function). So: data only.
  (An engine change, e.g. a `"card"` selector in `frame_for`, would allow a nicer syntax but the mod would then need a patched exe.
  Not done; decide later if wanted.)
- **Names are never overridden.** `cards.c` (`add_entry`, ~line 1557) sets `names[id]`, `descriptions[id]`, art, password back to
  "none" for a `replace` entry that does not give them, so an *earlier* mod's custom name would be reset (only `notes` has a shortcut).
  So the mod has `"priority": -1000`: it loads before every other mod, nothing is earlier to reset, a later mod's entry for the same
  card wins, and our tags survive unless that entry has its own `tags`. Checked: the 24 entries load as "card 364 Black Luster Soldier
  replaced" with the retail names, and a user mod after it resolves `"Thousand Dragon"`/`392` with no warnings.
- **Ritual monsters** = the 24 results of the disc's ritual table (`tools/pc/fm_editor` `decode_rituals` on the retail disc):
  356, 357, 360, 362, 364, 365, 374, 380, 701-706, 708-710, 715-720, 722. Shipped as `cards` entries tagging them `ritual`.
- Options 1-3 from the first option list (ritual spell / ritual monster / effect monster colour switches) were dropped by the user: the
  art is fixed per kind. Kept: `full_bleed` and `ritual_own_frame` (ritual spell blue vs green) which exist from v0.3.0's own HD manifest.
